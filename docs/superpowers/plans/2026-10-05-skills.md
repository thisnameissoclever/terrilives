# Skills Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every person a content-defined set of skills with a level and progress that rise by doing tagged activities, make the existing capability traits read their fumble chance from those skills instead of a private number, and show skills in the Sim sheet.

**Architecture:** A new content file `content/skills.toml` compiles into `ContentPack.skills`. A sparse per-person component `Skills(Vec<(u32, f32)>)` holds practice per pack skill index; a pure ladder function derives level, progress and mastery from practice and two tuning numbers. Practice rises at the three completion sites that already call `learn_and_manage`. `roll_fumble` reads mastery for the skill whose tag matches the capability trait. Practice is saved in an appended optional V5 field (`skills: Option<SavedSkills>`) by authored id, seeded once from capability states when the field is absent, and hashed in a sparse tagged block `skills-v1`. The web shell gains a Skills disclosure in Overview and the Traits panel's "Skill {n}%" reads mastery.

**Tech Stack:** Rust workspace (`terri-data` content compiler with `build.rs`, `terri-core` components and save records, `terri-sim` systems, `terri-wasm` boundary), postcard wire format, TypeScript web shell under `web/` (Vite 8, Vitest 4, fake-DOM tests).

**Spec:** `docs/specs/2026-10-05-skills.md` ([SK-model], [SK-learning], [SK-capability], [SK-save], [SK-hud], [SK-content], [SK-evidence]).

## Rulings

1. **Practice is the single stored number; level and progress are derived.** A ladder with `skill_level_cost` and `skill_level_growth` in `content/tuning.toml` turns practice into level and progress. The shipped ladder is flat (`skill_level_growth = 1.0`), so mastery equals practice and capability wearers keep their old learning pace until the owner tunes it. Cost if wrong: retuning the ladder re-levels everyone, which the owner can accept or change before any later consequence slice depends on levels; lowering the ladder caps saved practice at the new top on load.
2. **The capability trait's saved state becomes inert when a skill carries its tag.** It stays in the frozen save record and in the per-entity hash row untouched, but play neither reads nor raises it; the roll reads skill mastery. Cost if wrong: the inert number stays saved for nothing.
3. **An absent save field seeds practice from capability states once; a present field never seeds.** Cost if wrong: a person's seeded practice could differ from what the owner expects by the inverse ladder's rounding, which is below one f32 step of mastery.
4. **Skill ids are not in the content fingerprint.** Adding or removing a skill never invalidates a save; an unknown id in a present field refuses the load like an unknown trait id.
5. **The Skills view is a collapsed disclosure in Overview**, beside "Personality, habits and bed", not a new sheet tab: it avoids changing `SimPanel` and the compact HUD, which another worktree is editing.
6. **The Edit housemate removal note changes** from "Removing a trait forgets its progress." to "Removing a condition forgets its severity. Skills are kept." because capability progress now lives in the skill.

# Completed-job log anchor design review

Design approved with the concrete contract below. Replacing an unavailable active-run archive with a completed-job availability anchor addresses the lifecycle defect. Accepting a failed request, omitting the current run or selecting a convenient replacement would not.

I read `github-transport-better-way.md` and the current recovery, orchestration and fixture-tool wiring. No implementation, test, API request, Git operation, browser action or native work was performed. The supplied active-run 404 is host-credential evidence; the failed Actions preparation did not retain its exact HTTP status.

1. **Separate inventory from availability.** First authenticate the original plan, retain its recording, restore the selected snapshot and collect authenticated original references. Finish complete run/artifact/job/failure inventories independently of the availability signal. Only then choose anchors from that authenticated state. A metadata-only inventory pass may precede this preparation, but acceptance must require the availability pass for every referenced run, including the active current run.
2. **Choose once and retain the choice.** For a run without a recorded anchor, choose the earliest required original producer by attempt and numeric job ID before probing. Preserve that selected identity across snapshots and later evidence ingestion. A failed or missing selected log is terminal for that check; never search for a newer successful alternative. Store the anchor's run, attempt, job ID, selection basis, original observation and applicable retention/expiry binding separately from production records. Revalidate its binding and original expiry on continuation. A process-local cache alone cannot preserve this contract across attempts.
3. **Handle the receipt-free continuation explicitly.** A new current continuation can reuse the original plan without producing a new `MUTATION_PLAN` receipt. If it has no required original producer, authenticate its unique completed successful planning job against the current repository, run, exact planning attempt, expected planning name and already-authenticated workflow identity. Retain that planning job as the run's availability-only anchor. After preparation produces an original artifact, keep the earlier planning anchor; changing to the new producer could conceal loss of the original selected log. Never choose the current in-progress preparation or aggregate itself. A missing, foreign, skipped or incomplete planning job refuses.
4. **Authenticate completion rather than infer it.** Existing retained log entries do not all contain completed job metadata. Plan/tool originals are not covered by worker inventories. Use an already-authenticated retained job row when available, or fetch the selected exact job's metadata and charge that real request. Require its job ID, run ID and attempt to match the selected anchor and its status to be completed. An artifact receipt or the existence of retained log bytes alone does not establish completion. Failed producer policy remains governed by the complete failure inventory; probing a completed failed job cannot turn it into accepted evidence.
5. **Keep the transport narrow.** The HTTP adapter receives the validated exact job identity and requests only its repository job-log endpoint. It charges one request, disables redirects and accepts only a 302 with a valid HTTPS destination without user information. It never follows or persists the signed location, forwards credentials to it, prints raw log bytes, retries, or caches failure. Cache successful probes by the exact selected identity, not just a run ID. Errors report the safe repository/job identity and status or sanitized transport category; omit credentials, signed URLs and response bodies. Actual HTTP-branch tests must inject only the opener/response boundary, covering valid and malformed redirects, missing Location, 401/403/404/429/5xx and transport errors.
6. **Preserve the limited claim.** A successful probe establishes that GitHub currently issued a location for that selected completed job. It does not fetch the body, establish all historical body availability, prove future durability, authenticate a new producer receipt or add mutation coverage. All original bytes, hashes, artifact metadata, original retention, exact source/runtime/tool bindings and terminal-failure inventories remain required.

The bounded same-token preflight belongs before Cargo in the existing fixture-tool execution path. It needs no new heavy job, dependency edge, permission, concurrency group or cap.

Use it only for this diagnostic. Do not repurpose qualification inputs or store a dated historical job ID in maintained code. Authenticate the current `changes` job as a completed successful predecessor in the current run. If its execution came from an earlier attempt retained by a targeted rerun, bind that actual attempt explicitly rather than pretending it ran in the current attempt.

This is historical availability diagnostic evidence, not historical recipe or workflow qualification. Seven requests do not include a separate historical-run workflow authentication; do not claim that stronger proof.

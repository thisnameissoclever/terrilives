## Failure and adopted contract

The actual fixture's tool and plan succeeded, but preparation failed because the adapter required an active workflow run's whole-run log archive to produce a download redirect. The failed Actions job did not report its HTTP status. Root's separate host request observed 404 while that workflow was active; that observation uses a different credential and does not establish the Actions token's status.

Adopt ALT1: authenticate and retain all original evidence, complete the run/artifact/job/failure inventory, then require a fresh non-following job-log redirect for one stable authenticated completed-job anchor per referenced run. Include the current run. An anchor proves only issuance of a current location for that selected job. It does not retrieve the body, replace an original receipt, renew retention or add mutation coverage.

The final design resolves the diagnostic input: a supplied optional historical job ID produces the seven-request same-token path. Empty input produces the five-request current-changes-only path and explicitly reports historical coverage absent. There is no automatic historical discovery, hardcoded ID, qualification-field reuse or manufactured request.

## Stable retained anchor representation

Add a bounded, explicit top-level map such as `log_availability_anchors`, keyed by run ID, separate from producer logs and production records. A proposed exact compact row includes version, repository, run ID, numeric attempt, decimal job ID, selection basis, expected job name, original selection/observation time, original retention days and fixed expiry. For an original-producer basis, also bind the retained producer-log path, its original SHA-256 and original observation time. Retain compact completed-job metadata needed for validation, rather than the full API response with steps and incidental URLs. Exact keys and types should be fixed by the implementation brief.

1. For a run without an anchor, choose the earliest required authenticated original producer by attempt and numeric job ID before any probe. Candidates come from authenticated required retained log references, not arbitrary job names. Resolve ties deterministically and reject conflicts. Validate positive IDs, repository/run/attempt linkage, original byte digest/reference and original retention. Require completed non-skipped job execution; an artifact receipt or retained bytes alone is insufficient.
2. Where an already-authenticated retained job row exists in worker/native/aggregate inventories, reuse its completion evidence. Plan/tool/qualification originals are not all represented in those inventories. The simplest bounded alternative is one exact `repos/{repository}/actions/jobs/{job_id}` metadata GET for the selected anchor, charged through WorkflowAPI. Validate ID/run/attempt/status and relevant name against the selected identity, and reject the current in-progress preparation or aggregate. Never try a second candidate after metadata or redirect failure.
3. A new current continuation can reuse the original plan while emitting no new `MUTATION_PLAN` receipt. Only when it has no required original producer, authenticate its unique completed successful planning job in the current repository/run and exact actual planning attempt, with the expected scope-specific planning name and already-authenticated workflow identity. A bounded job listing may be needed to discover that identity. Bind the actual attempt rather than inventing the current preparation attempt. Missing, ambiguous, foreign, skipped or in-progress planning refuses.
4. Persist this planning identity as availability-only evidence. It must remain the selected anchor after preparation uploads its first artifact, after aggregation and after snapshot reload. Do not replace it with a new producer, recompute a more convenient minimum or rely only on `WorkflowAPI.probed`. A deterministic first-attempt formula is not adopted: a successful planning job can legitimately belong to another actual attempt, and using a different later job could hide loss of the originally selected one.
5. Preserve the original anchor observation and expiry on continuation. A fresh redirect may update a separate bounded latest-observation field only if the schema/projection accounts for it; it must not replace or extend the original lifetime. Original-producer expiry binds to the retained log's original expiry. Planning-only expiry binds to the authenticated run creation and the original recorded runner retention, conservatively constrained by current retention as with existing evidence. Every anchor must cover the unchanged campaign end plus recovery margin.
6. Validate persisted anchor types, exact allowed key set, run set, original-reference binding, completion identity and immutable selection on load and before reuse. Reject deletion/substitution of an existing anchor even when a newer completed job is available. Do not put availability-only metadata into `data["logs"]` with a synthetic producer receipt or artifact ID.
7. The intended referenced-run budget is at most ten total: eight chain runs plus two proof-source runs. Current code separately checks chain length and source_runs length before taking their union. The anchor pass must explicitly bound that union as well; otherwise those separate checks alone can permit more than ten distinct entries. This preserves the documented total bound rather than widening it. Anchor-map keys cannot silently omit or add runs outside that authenticated union.

## Narrow HTTP transport

Replace `WorkflowAPI.probe_logs(repository, run_id)` with an exact validated job-identity operation, for example `probe_job_logs(repository, run_id, attempt, job_id)`. Anchor selection stays above the transport. Use one fixed repository job-log endpoint with the existing executing job's GH_TOKEN and `NoRedirect` opener. Charge one request before opening. Accept only status 302 and a valid HTTPS Location without username/password user information. Validate malformed ports/URLs without echoing them.

Never follow the Location, forward credentials to it, read/render the raw body, persist the signed URL, retry or cache failure. Cache success by exact repository/run/attempt/job identity. Report only safe resource identity, numeric HTTP status or sanitized transport category, Location-present/HTTPS booleans and timestamps. Do not interpolate an HTTPError/URLError string, headers, body, token or signed URL into the outer workflow failure JSON.

Add real HTTP-branch tests that patch only the opener/response boundary. Construct the actual Request and assert the exact API host/path and authorization destination, `NoRedirect` construction, one charged request and no response-body reads. Cover normal 302 and urllib HTTPError(302), absent/invalid Location, user information, malformed URL/port, 401/403/404/429/5xx and transport errors. A failed probe remains uncached; a successful exact identity is cached. Existing fixture `probe_logs` success lambdas must be converted for high-level accounting but are not transport evidence.

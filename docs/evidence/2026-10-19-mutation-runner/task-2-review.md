## Findings

1. **P1: The tool digest can identify a different executable from the one invoked.** `.github/scripts/mutation_runner.py:189-194` asks `cargo mutants --version`, then independently hashes `shutil.which("cargo-mutants", path=env.get("PATH"))`. Generation, selection and mutation execution also use `cargo mutants` at lines 186, 618 and 631. These are different resolution rules. Cargo 1.94.1 prepends `CARGO_HOME/bin` when that directory is absent from PATH; Python's `which` does not. See the installed-revision [Cargo source, `search_directories`](https://github.com/rust-lang/cargo/blob/29ea6fb6a/src/bin/cargo/main.rs#L330-L350).

   The bounded reproduction used an ordinary temporary directory. Its `bin/cargo-mutants.exe` was a byte-for-byte copy of the installed, unmodified stock tool. A separate directory prepended to PATH contained a copy of Windows `whoami.exe` named `cargo-mutants.exe`. `CARGO_HOME` pointed at the temporary root, whose `bin` directory was absent from PATH. Calling the real `installed_tool()` returned version `27.1.0`, accepted the SHA-256 of the renamed `whoami.exe`, and did not return the digest of the stock tool that actually ran. Observed assertions: `accepted_digest_is_whoami: True`; `accepted_digest_is_executed_stock: False`. No modified cargo-mutants binary was built, installed or executed.

   Resolve the executable once, hash those exact bytes, and invoke that exact absolute path for version, enumeration, selected enumeration and execution. Preserve the required cargo-mutants subcommand argument convention. Include a regression with divergent Cargo-home and PATH candidates; equal displayed versions must not permit a different executable to supply evidence. The currently approved binary's source/patch identity also remains an integration requirement when a tool change is authorized.

2. **P1: Passing calibration and execution do not revalidate the owned source copy.** Calibration verifies the clone before running phases at `.github/scripts/mutation_runner.py:515`, but its final source check at line 537 checks the original checkout. Slot execution likewise checks the clone before launch at lines 603-605, then checks only the original checkout after the controller at lines 641-642. Neither verifies that the files actually compiled stayed consistent with the fingerprint. Neither Cargo invocation uses `--locked`, so Cargo.lock drift is one concrete path; a test or build script can also write a tracked input in the owned clone. Original-checkout cleanliness cannot detect these writes.

   A bounded fixture created a clean disposable Git repository with tracked Cargo.toml and Cargo.lock, then called the real `calibrate()`, including real Git clone/checkout and the real owned-process controller. Only the Cargo test child was replaced with a short Python child that rewrote the clone's Cargo.lock and exited zero. Tool-version identity was stubbed because this fixture did not run Rust. Both phase logs recorded the changed lock. Calibration still returned `build_status: 0` and `test_status: 0` and wrote a receipt bound to the original inventory. The original lock and source checkout remained unchanged and clean. Observed assertions: `calibration_accepted: True`; `owned_copy_changed: True`; `original_lock_unchanged: True`; `original_checkout_clean: True`.

   Verify calibration's owned inputs after each phase and before accepting its receipt. Prevent Cargo lock updates in both calibration and mutant commands, keeping their effective command contracts aligned. For mutation execution, account explicitly for the active mutation that may remain after an interrupted process; simply requiring a clean clone after interruption would reject valid checkpoints. Detect unexpected changes to other tracked inputs and bind each retained result to the immutable input contract. Add fault tests that change Cargo.lock and another tracked input while leaving the protected original checkout clean. Reject the resulting receipt or checkpoint. Do not merely reset the clone and accept the evidence produced before the reset.

3. **P1: Aggregate acceptance can bypass the current attempt's source-change refusal.** `.github/scripts/mutation_runner.py:661-686` never receives or verifies the current root/context. It validates recovered records and current survivor-baseline bytes, then declares exact coverage. The current-worker artifact check at lines 671-678 runs only when coverage is incomplete. If a continuation restores a completed earlier manifest but current workers reject a changed source before creating bundles, the aggregate can still return `complete`. The CLI accepts `--root` for aggregate but does not use it for source validation. `authenticate_run()` verifies that each declared commit/tree exists; it does not prove that the new commit has the original computation fingerprint.

   The bounded reproduction used the existing injectable artifact API fixtures and actual archive digests, producer receipts, job-log checks, report validation and delta merging. It supplied all 17 identities across eight authenticated bundles from run 100, then appended run 200 as a valid explicit successor with a different commit/tree and unchanged workflow. Run 200 had no artifacts; its eight fixture job records had failure conclusions. Only the clock passed to recovery was fixed to the fixture date. The real aggregate returned `{"completed":17,"failing":0,"planned":17,"reason":"exact_coverage","remaining":0,"state":"complete"}` and never queried run 200's jobs. This fixture proves the acceptance bypass; it does not claim to have executed changed Rust source.

   Before accepting results for the current checkout, independently compare its clean input inventory and execution contract with the planned fingerprint, including when all records come from predecessors. Keep permitted documentation-only changes possible by comparing computation inputs rather than demanding identical whole-tree SHAs. Carry a current-attempt source-validation failure into aggregate failure even when prior coverage is complete. Add regression cases for changed native inputs, unchanged-input documentation commits, and complete prior coverage with a failed current validation. An explicitly historical report may describe the old campaign, but must not become the current checkout's acceptance check.

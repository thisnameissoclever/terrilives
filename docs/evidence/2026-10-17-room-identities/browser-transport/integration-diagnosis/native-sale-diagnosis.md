# Refused-sale fixture diagnosis

The failing test asks a housemate to use object 15, the shipped floor lamp, at interaction 0. The lamp has no interaction. The command API accepts a well-formed queued request; that does not establish an executable action. This is a concrete fixture precondition failure. Static inspection predicts that private current-save validation rejects the resulting intent before adoption, leaving the live sale receipt empty. It does not identify a receipt-transfer defect for valid input.

Scope: frozen checkpoint `23bf404873b2e450658b8858d8a4395f2656686d`. Parent's receipt identifies actual release module SHA256 `6c0562aca59fe17b20000845ebeddb71337859b2b39bd8e212a10ec5ab3154c1`. ## Exact native path

1. `SimBridge.useObject` documents queue acceptance and intentionally does not range-check the interaction (`web/src/bridge.ts:1545-1561`). `drain_ordinary_commands` resolves the person and object, copies the interaction index and creates the intent (`crates/terri-sim/src/systems/command.rs:527-600`). Invalid interaction removal belongs to later `serve_intents`; a paused command flush does not run that gameplay stage.
2. The queued sale makes `Sim::flush_commands` enter ordinary atomic construction (`lib.rs:2325`; `build_transaction/ordinary.rs:91-101`). The all-certainly-refused shortcut is not taken: UseObject falls through to false (`build_transaction/commands.rs:151`). Preparation captures a complete V16 baseline without pending input, restores a private candidate and then replays both commands (`ordinary.rs:153-174`).
3. `systems/lot_edit.rs:29-35` flushes preceding ordinary commands before dispatching construction. `flush_ordinary` applies deferred ECS inserts before returning (`lot_edit.rs:298-307`), so the new intent is visible to sale validation. `placement/sale.rs:75-95` refuses an object named by any IntentQueue. `sale::commit` always writes a SaleResult, including InUse with no payout (`sale.rs:122-149`). Therefore the source predicts that the refused-sale receipt exists in the private candidate.
4. The candidate is then captured and strictly restored for validation (`ordinary.rs:188-194`). V6 restore calls `action_refs::remap` (`save/v6.rs:237-243`). The action mapper visits each saved intent, indexes the model's flyout and returns InvalidContentReference when row 0 is absent (`save/action_refs.rs:412-443`). The floor lamp's flyout is empty. Current final maintenance does not run `serve_intents` to remove this request first.
5. That error returns before `PreparedOrdinary` is produced. `run_atomic_drain` consumes the original command batch and records the typed validation error (`ordinary.rs:118-148`); it does not install the candidate or copy its feedback. The original fresh world's `last_sale_result` therefore remains None. This is the predicted explanation of the observed null, not an observed error code from the failing run.
6. On successful preparation, changed candidates are installed; unchanged candidates use `copy_feedback`. The latter copies the entire LotEditState, including the sale result (`ordinary_runtime.rs:16-35`). Adoption retains the candidate LotEditState, changes its revision and carries the Build epoch (`lib.rs:1605-1625`; `build_transaction.rs:164-176`). No inspected successful path clears this receipt.

## Browser-side consumption check

`SimHandle::last_sale_result` is an immutable getter over LotEditState and maps None to an empty vector (`crates/terri-wasm/src/lib.rs:1619-1633`). `SimBridge.lastSaleResult` maps only that empty vector to null (`web/src/bridge.ts:602-606`). `FurnitureBuilder.afterCommands` reads the result and uses read-only placement/sale previews when requerying (`web/src/ui/builder.ts:250-276,338-352`); it does not take the native sale result or native build error. Thus source inspection gives no evidence that afterCommands consumes the receipt.

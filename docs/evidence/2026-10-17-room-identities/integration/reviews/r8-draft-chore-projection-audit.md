## Recommendation and remaining proof

1. Close this as **diagnostic projection with no demonstrated load-bearing defect**, retaining the distinction between stored ownership and a derived row. Do not infer a lost assignment or reroll from the `u32::MAX` fallback. Do not claim the transient row is the final review result either.
2. In R8's doc work, clarify the existing contract: “Saved assignments and gameplay consequences remain unchanged until Confirm. Chores are unavailable during Build; raw diagnostic chore rows may reflect draft object positions and are not a confirmed assignment report.” This report proposes that clarification only; it does not edit the contracts or approve new player copy.
3. A focused native control should establish a valid assigned dirty table, begin Build, accept its cross-room move, then repeatedly query rows/location/history. Compare full raw capture before/after those queries, live SavedChores and every random stream, committed bytes, clock, task claims and prepared-token validity. Allow the derived row to change. Compare a query-heavy branch with an otherwise identical branch that never queries, through cancellation, confirmation and the first ordinary resumed tick. Require the same adopted ownership/continuation and preserved active-object refusals. Query-heavy versus query-free comparison tests the actual boundary without imposing a new frozen-query contract.
4. Existing source controls cover nearby boundaries: `build_transaction.rs:754` freezes ticks/committed saves; `build_transaction/cases.rs:750` blocks unrelated gameplay without mutating raw draft; `:1098` reconciles a moved counter with unchanged walls; `:383` refuses stale submit without draining new input; `:489` checks public snapshot writers. They do not independently establish the exact R8 table/query-heavy sequence. No new runtime control ran in this read-only audit.
5. If a later reproduction exposes unconfirmed rows in the player board or uses them for gameplay admission, fix that consumer at the native transaction seam using the existing committed authority, or retain the Build guard that should exclude it. The existing `committed_projection` (`build_transaction.rs:626-634`) demonstrates available authority if a committed query is actually required. A second stored baseline/cache or a second ownership matcher would add synchronization risk without addressing a demonstrated current effect.

**Next steps**: R8 can document the diagnostic boundary and retain or add the focused native comparison under its normal verification ownership. No production change is justified by this observation alone.

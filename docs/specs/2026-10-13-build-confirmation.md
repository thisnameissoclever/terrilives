# Build confirmation and cancellation

Build mode treats the paused simulation as a draft. Existing furniture, wall, window, room, floor, and store actions update that draft. Place accepts an individual furniture preview into the draft. Switching selections or tools never makes a draft permanent.

The bottom of the build flyout contains red Cancel followed by green Confirm. Confirm settles queued edits and any pending furniture placement, keeps the changes and leaves Build. When the final arrangement splits, merges, or opens existing rooms, it presents the room-change review before adoption and exit. Back to build retains the draft and cancels the pending exit. Confirm changes accepts the exact reviewed arrangement and completes the exit. Cancel restores the baseline and leaves Build. A refused confirmation or rollback keeps Build open and paused with its error. Re-entering Build starts a new batch from the last confirmed arrangement.

Every other way out reaches the furniture builder's exit, whose guard is `BuildExit.gate` in `web/src/ui/build-exit.ts`: Exit build, the Build button, and Escape with nothing selected. With nothing pending, Build closes at once. Otherwise, Leave Build mode? asks first. Its buttons are stacked: neutral Keep building, red Discard changes, then green Confirm changes directly below Discard changes. Keep building has initial focus and is also what Escape chooses, wherever focus is on the page. It preserves the draft and returns focus to the opener or game view. Confirm changes confirms and leaves; Discard changes restores the baseline and leaves. Changes are pending when native dirtiness reports authored edits or pending commands, an unsettled browser preview remains, or room-review choices are retained. Public save bytes contain only the committed baseline.

Entering Land from another Build tool uses the same decision dialog when changes are pending, headed Switch to Land? rather than Leave Build mode? Keep building or Escape preserves the current tool and draft. Confirm completes any room review and adopts the edits; Discard restores the baseline. After either successful decision, Land opens in a fresh Build session without advancing gameplay. A clean tool switch needs no dialog. Failed decisions, review Back, loading, graphics interruption and superseding actions must not leave a stale Land destination that fires later. Tool switching must ask before clearing a preview.

Escape first clears the current tool's selection and only tries to leave when nothing is selected. A held Escape counts once: its repeats do nothing, wherever focus is, so a dialog opened by a held key stays open until a fresh press. The contextual Cancel beside a selection clears that selection the same way, never leaves Build mode, and keeps every other pending change. Only the footer's Cancel and the dialog's Discard changes discard the batch. When Confirm is refused while a furniture move is shown, the status line asks the player to move it somewhere it fits or choose Cancel beside it.

A discard resets every tool as a Load does, so a purchase dropped with the draft cannot leave a tool waiting for its result. When a pointer click opens or closes the dialog or leaves Build mode, by any route including Exit build with nothing pending, the clicks that continue that click's run are ignored for up to a second, wherever they land. So the second click of a double-click does not reach the game. A double-click on Exit build in the phone dock, where Discard changes then sits over it, leaves the dialog open with Keep building focused instead of discarding, and a double-tap is meant to do the same when the browser counts the second tap as a second click. The click that caused it is read before any confirm, discard or redraw work, so slow work cannot lose it, and a later keyboard action never clears it. The browser's click count decides what continues a run: a double-click's second click counts 2. A quick second tap at the same place is expected to count 2 as well, based on how Chromium's gesture handling counts repeat taps; this has not been checked on a touch device. A click whose count does not go past the guarding click's starts a new run: it goes through at once and ends the guard, so a fresh click on a dialog button, or a fresh double-click soon after, works. Keyboard actions do not arm the pointer guard. A separate activation guard suppresses repeated Enter and Space across opening, Keep focus restoration and completion until a fresh activation press. When the graphics device is lost, the dialog closes as Keep building so the recovery message and Retry graphics are not hidden behind it.

The native simulation owns the baseline, accepted-command journal, pending room names, and prepared review. Browser `BuildSession` settles previews and presents the controls. Confirm replays accepted edits from the baseline into a private candidate, resolves final room membership once, and validates that candidate before adoption. A review token identifies its session, revision, and preparation; an obsolete token cannot commit another arrangement. See [room identity and naming](2026-10-17-room-identities.md).

Retained explicit review choices also count as pending input when deciding whether to leave Build. Reversing wall edits exactly can make native geometry clean while a name entered in review remains pending. Exit still asks first. Keep building preserves that name, and Confirm obtains and displays a fresh review before adoption; Cancel or Discard clears it explicitly.

All persistence paths request committed native bytes, including manual Save, visibility-triggered saving and autosave. Dirty drafts and open reviews never replace the committed save. Graphics-device recovery preserves the native handle and its transaction.

Successful Load replaces the baseline with the loaded household and clears the old journal. When Build is active, the privately loaded household settles its saved command stream once, without advancing time, before establishing the fresh baseline, just as at Build entry. Rejected Load or settlement preserves the live household and transaction. A failed preparation, commit, or rollback keeps Build open and paused, reports the failure, and retains the baseline.

Cancellation clears queued draft commands and tool receipts, restores funds and owned objects, and refreshes architecture, floor resources, selection, lighting, and audio. Store purchases, sales, and book transactions made during Build belong to the same batch. Household editing, chores, death settings, and Sim-detail controls are unavailable while the batch is active so cancellation cannot silently undo unrelated changes.

Room names, chore assignments, and room-entry consequences remain unchanged during edits. Detection compares the last confirmed rooms with the final draft, so removing and restoring a wall in one batch preserves identities and names. New unrelated enclosures receive numbered names at Confirm. The player can re-enter Build to rename them. Outside counts as one shared room; grass remains ineligible for floor cleaning.

This preserves saved assignments and gameplay consequences. Chores are unavailable during Build; raw diagnostic chore rows can reflect draft object positions and are not a confirmed assignment report. Confirm reconciles the private candidate from the native baseline rather than adopting those diagnostic rows.

Physical room outlines include the owned lot perimeter. Perimeter solids are saved, drawn, and validated as physical architecture. They do not become movement-grid barriers between an owned tile and an out-of-bounds tile: off-lot movement is already disallowed. Doorways remain interior-only. The Wall tool can remove and rebuild explicit perimeter solids while preserving the original implicit rear shell. The original implicit rear house shell is not duplicated. Existing saves are preserved without guessing where old incomplete rooms were meant to have walls.

The window action is Place Window, and contextual cancellation controls read Cancel. Functional labels describe the action without humor.

Verification covers committed versus draft save bytes, cancellation before and after command draining, chained edits, confirmed-batch retention across visits, rejected rollback, successful and rejected Load, perimeter geometry, and save round trips. Browser checks cover desktop and compact controls, neutral Keep building, stacked decision order, footer exit and clean Land entry after resolving edits. Controller and actual-page tests cover delayed room review, each dialog answer, Escape, focus, stale destination cancellation, failed Confirm or rollback, contextual selection cancellation, pending purchases, double-clicks and graphics recovery.

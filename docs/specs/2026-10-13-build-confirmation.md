# Build confirmation and cancellation

Build mode treats the paused simulation as a draft. Existing furniture, wall, window, room, floor, and store actions update that draft. Place accepts an individual furniture preview into the draft. Switching selections or tools never makes a draft permanent.

The bottom of the build flyout contains red Cancel followed by green Confirm. Confirm settles queued edits and any pending furniture placement. When the final arrangement splits, merges, or opens existing rooms, it presents the room-change review before recording a new baseline. Back to build discards that review and retains the draft. Confirm changes accepts the exact reviewed arrangement. Footer Confirm and review Confirm keep paused Build open. Cancel restores the most recent baseline and keeps paused Build open. Exit build opens the existing exit dialog when changes remain; its Confirm commits and then leaves, its Discard restores and leaves, and Keep building retains the draft. Review Back clears pending exit intent. Confirming one batch and cancelling the next keeps the first batch.

Every other way out reaches the furniture builder's exit, whose guard is `BuildExit.gate` in `web/src/ui/build-exit.ts`: Exit build, the Build button, and Escape with nothing selected. With nothing pending, Build mode closes at once. While changes are not confirmed, a modal dialog, Leave Build mode?, opens instead. Keep building has focus when it opens and is also what Escape chooses, wherever focus is on the page, without touching the build behind the dialog; Build mode stays open and focus returns to the control that asked to leave, or to the game view. Confirm changes confirms and leaves, staying open with the reason when Confirm is refused. Discard changes restores the baseline and leaves. Changes are pending when the native semantic dirty query reports authored changes or pending native build input, or an unsettled browser tool preview remains. Public save bytes deliberately contain the committed baseline.

Escape first clears the current tool's selection and only tries to leave when nothing is selected. A held Escape counts once: its repeats do nothing, wherever focus is, so a dialog opened by a held key stays open until a fresh press. The contextual Cancel beside a selection clears that selection the same way, never leaves Build mode, and keeps every other pending change. Only the footer's Cancel and the dialog's Discard changes discard the batch. When Confirm is refused while a furniture move is shown, the status line asks the player to move it somewhere it fits or choose Cancel beside it.

A discard resets every tool as a Load does, so a purchase dropped with the draft cannot leave a tool waiting for its result. When a pointer click opens or closes the dialog or leaves Build mode, by any route including Exit build with nothing pending, the clicks that continue that click's run are ignored for up to a second, wherever they land. So the second click of a double-click does not reach the game. A double-click on Exit build in the phone dock, where Discard changes then sits over it, leaves the dialog open with Keep building focused instead of discarding, and a double-tap is meant to do the same when the browser counts the second tap as a second click. The click that caused it is read before any confirm, discard or redraw work, so slow work cannot lose it, and a later keyboard action never clears it. The browser's click count decides what continues a run: a double-click's second click counts 2. A quick second tap at the same place is expected to count 2 as well, based on how Chromium's gesture handling counts repeat taps; this has not been checked on a touch device. A click whose count does not go past the guarding click's starts a new run: it goes through at once and ends the guard, so a fresh click on a dialog button, or a fresh double-click soon after, works. Opening or closing the dialog from the keyboard ignores nothing. When the graphics device is lost, the dialog closes as Keep building so the recovery message and Retry graphics are not hidden behind it.

The native simulation owns the baseline, accepted-command journal, pending room names, and prepared review. Browser `BuildSession` settles previews and presents the controls. Confirm replays accepted edits from the baseline into a private candidate, resolves final room membership once, and validates that candidate before adoption. A review token identifies its session, revision, and preparation; an obsolete token cannot commit another arrangement. See [room identity and naming](2026-10-17-room-identities.md).

All persistence paths request committed native bytes, including manual Save, visibility-triggered saving and autosave. Dirty drafts and open reviews never replace the committed save. Graphics-device recovery preserves the native handle and its transaction.

Successful Load replaces the baseline with the loaded household and clears the old journal. When Build is active, the privately loaded household settles its saved command stream once, without advancing time, before establishing the fresh baseline, just as at Build entry. Rejected Load or settlement preserves the live household and transaction. A failed preparation, commit, or rollback keeps Build open and paused, reports the failure, and retains the baseline.

Cancellation clears queued draft commands and tool receipts, restores funds and owned objects, and refreshes architecture, floor resources, selection, lighting, and audio. Store purchases, sales, and book transactions made during Build belong to the same batch. Household editing, chores, death settings, and Sim-detail controls are unavailable while the batch is active so cancellation cannot silently undo unrelated changes.

Room names, chore assignments, and room-entry consequences remain unchanged during edits. Detection compares the last confirmed rooms with the final draft, so removing and restoring a wall in one batch preserves identities and names. New unrelated enclosures receive numbered names at Confirm. Build remains open so the player can select and rename them in another batch. Outside counts as one shared room; grass remains ineligible for floor cleaning.

Physical room outlines include the owned lot perimeter. Perimeter solids are saved, drawn, and validated as physical architecture. They do not become movement-grid barriers between an owned tile and an out-of-bounds tile: off-lot movement is already disallowed. Doorways remain interior-only. The Wall tool can remove and rebuild explicit perimeter solids while preserving the original implicit rear shell. The original implicit rear house shell is not duplicated. Existing saves are preserved without guessing where old incomplete rooms were meant to have walls.

The window action is Place Window, and contextual cancellation controls read Cancel. Functional labels describe the action without humor.

Verification covers committed versus draft save bytes, cancellation before and after command draining, chained edits, confirmed-batch retention, rejected rollback, successful and rejected Load, perimeter geometry, and save round trips. Browser checks cover desktop and compact controls, including the button order and Exit behavior. Unit checks with a fake page cover the footer leaving after Confirm and Cancel, each dialog answer, Escape, focus, leaving with nothing pending, a refused Confirm or failed rollback keeping Build mode, the contextual Cancel keeping the batch, a purchase on its way, double-clicks, and closing the dialog for graphics recovery.

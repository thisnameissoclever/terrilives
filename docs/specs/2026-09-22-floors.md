# Floors: the player chooses what each tile's floor is

[B-floors] in `FEATURES.md`. The per-tile Floors tool shipped in PR 128. The 2026-10-01 material release replaced placeholder interior art with authored boards, tiles and carpet; its evidence is in `docs/assets/review-evidence/architecture/verification.md`. Current worlds save base surfaces explicitly and treat original indoor floor as editable ground.

## [FL-content] A covering is authored content

`content/lot.toml` carries yard and street colour settings, exposed as `yard_look` and `street_look`. The authored grass and asphalt apply those settings relative to their baked appearance; the historical sprite path retains its absolute colour shifts. Coverings are a list beside them, each with a plain name for the tool and the same three numbers. The covering IDs are **Boards=1**, **Tiles=2**, **Carpet=3**, and **Outdoor patio=4**. Existing IDs retain their material artwork.

A covering is authored with a name and the three numbers; its id is its position in the list, counted from 1, and is not written in the file. The list therefore grows by appending, and the compiler refuses a covering with no name, two that share a name, or numbers outside a colourway's ranges, exactly as it refuses a bad `yard_look`. The coverings ride at the compiled pack's tail, so no established pack byte moves.

## [FL-command] Painting a tile is a command

`SimCommand::SetFloor { x, y, covering }` is appended after the commands that exist, so no earlier wire code moves. `covering` is 0 for Remove and 1 upward for coverings in content order. Remove clears the covering and converts underlying indoor base floor to grass; an existing grass or street base remains. The simulation refuses a tile off the lot and a covering the content does not have. Removing floor changes saved material eligibility and future arrival targets without creating a wall or blocking the tile.

Like other lot edits, it applies in stream order and records its result for the tool. A changed covering or base surface increments the lot revision. Ground instances update while the renderer retains accepted base textures and static resources. A no-op changes no revision.

## [FL-save] Base surfaces and coverings are saved separately

The historical `SaveSnapshotV5` introduced `floors: SavedFloors`, a sorted sparse list of `(x, y, covering)`, appended last for the reason `sleep_pressure` was: postcard writes a struct's fields back to back, so a payload written before this field existed is a prefix of one written after it, and the loader reads the prefix and defaults the tail rather than rejecting every save anybody has.

Sparse, and sorted by tile, so a house nobody has painted costs one byte and two identical houses save identically whatever order their tiles were painted in. In current worlds a tile with no covering entry draws its explicit saved base surface under [OS-yard]. Historical adoption derives those surfaces from the restored layout once, then saves them independently of the original house rectangle. Supported older covering choices remain. All loaded layouts use the authored floor artwork while frozen fixture bytes retain their historical meaning.

The loader refuses a floor entry off the lot, out of order or repeated, as it refuses a bad wall record: those describe a save that cannot be true. An entry naming a covering the content no longer has is a different thing, a content edit rather than a corrupt save, so that tile loses its covering and the rest of the house loads, exactly as an object whose colourway is gone loads as drawn. Refusing the save instead would make one line removed from `lot.toml` brick every save that used it.

The frozen historical tail reader pads only a payload that ran out of bytes. Any other historical decoding failure means the bytes stopped making sense partway, and padding such a payload would rescue a corrupt save rather than an old one: a name whose length byte grew by one eats the floors terminator, and a pad puts one back. Current versioned envelopes use explicit version dispatch and strict payload validation; this historical tail rule does not authorize padding a truncated current record.

## [FL-draw] Authored materials with stable covering IDs

Boards=1, Tiles=2 and Carpet=3 remain unchanged; Outdoor patio appends ID 4. Zero removes a covering and indoor base floor under the current [FL-command] rule. All loaded layouts draw authored material patches with world-aligned phase. Outdoor patio uses rectangular gray paving and does not change a tile's enclosure. Shared world-space diamond corners prevent gaps at fractional pan and zoom. Each tile remains one instance. Saved indoor base floor uses pale tile, grass uses its seasonal appearance and street uses asphalt. Historical floor sprite data remains unchanged, and the renderer still supports its architecture-disabled compatibility path; the game enables authored floors after Load.

The accepted artwork already contains its starter hue. Runtime content colour tuning is applied relative to that baked baseline, avoiding a second application of the same colour. Finish descriptors separate geometry, pattern and palette; only active alternate patterns consume texture slots. This supports catalogue extension without claiming a new finish library or wall-painting interface.

Outdoor patio uses an append-only descriptor in `assets/models/architecture/outdoor-patio.json`. The offline importer verifies the pinned architecture source and existing material identities before appending it. Accepted export receipts, historical floor geometry, and texture files remain unchanged.

## [FL-tool] The Floors tool

Build offers Floors alongside its other tools, including Land. A click selects and highlights a tile without changing it. Contextual covering buttons apply to the selection. Remove follows [FL-command]; Cancel clears the selection and waiting edit. Selecting a new tile does not automatically paint it. Number shortcuts request the corresponding covering only with a selection.

Before staging a native edit, the resource owner prepares any missing finish inputs. A still-current waiting edit resumes once after readiness or Retry. A different selection, covering, draft revision, household or tool invalidates that edit. Optional loading may finish and populate the cache after cancellation; it must not paint a canceled selection. Ready alternative coverings remain requestable after an optional choice fails.

The controller owns previews, native batches and results. Structured contextual feedback owns selected loading, refusal and Retry. When no tile is selected, the main-scene recovery owner keeps a failed chosen material's Retry available. These recovery surfaces are mutually exclusive. Clearing the selection can transfer material recovery without retaining the canceled edit. Progress comes from live resource state, rather than a copied persistent status string.

Finish preparation retains base textures, depth, registration and static support buffers, loads only missing inputs, and publishes a complete validated state atomically. A new-device recovery explicitly rebuilds the renderer and cancels the old waiting edit. Resource retirement follows submitted graphics completion.

## [FL-area] An area of tiles

Asked for by the owner on 2026-10-19. A second click on another tile, before anything is applied, makes the two clicks the opposite corners of a rectangle and selects every tile in it. Tiles that would take the chosen covering are ringed in the accepted tint and previewed in it; tiles that refuse it are ringed in the refused tint and left out. A covering button, a number shortcut or Remove then stages one `SetFloor` command for every tile in the rectangle that would change and that the simulation accepts, in bounded command batches. Contextual feedback reports how many tiles took the covering and the actual refusal when some did not. Once an area is chosen or a change lands, the next click starts a new choice; a second click on the same tile keeps one tile chosen.

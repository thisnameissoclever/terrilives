# Floors: the player chooses what each tile's floor is

[B-floors] in `FEATURES.md`. The per-tile Floors tool shipped in PR 128. The 2026-10-01 implementation replaces its placeholder interior art with authored boards, tiles and carpet. The command and save contracts below remain unchanged; final local evidence is recorded in `docs/assets/review-evidence/architecture/verification.md`.

## [FL-content] A covering is authored content

`content/lot.toml` carries yard and street colour settings, exposed as `yard_look` and `street_look`. The authored grass and asphalt apply those settings relative to their baked appearance; the historical sprite path retains its absolute colour shifts. Coverings are a list beside them, each with a plain name for the tool and the same three numbers. The covering IDs are **Boards=1**, **Tiles=2**, **Carpet=3**, and **Outdoor patio=4**. Existing IDs retain their material artwork.

A covering is authored with a name and the three numbers; its id is its position in the list, counted from 1, and is not written in the file. The list therefore grows by appending, and the compiler refuses a covering with no name, two that share a name, or numbers outside a colourway's ranges, exactly as it refuses a bad `yard_look`. The coverings ride at the compiled pack's tail, so no established pack byte moves.

## [FL-command] Painting a tile is a command

`SimCommand::SetFloor { x, y, covering }` is appended after the commands that exist, so no earlier wire code moves. `covering` is 0 for "whatever the tile would be without a choice", which is what the Remove button sends, and 1 upward for the coverings in content order. The simulation refuses a tile off the lot and a covering the content does not have.

Like every other lot edit it is applied in stream order, the drain records its result for the tool to read, and it bumps the lot revision so the renderer rebuilds.

## [FL-save] The choices are saved, sparsely, appended last

The save envelope, `SaveSnapshotV5`, stores `floors: SavedFloors`, a sorted sparse list of `(x, y, covering)`, appended last for the reason `sleep_pressure` was: postcard writes a struct's fields back to back, so a payload written before this field existed is a prefix of one written after it, and the loader reads the prefix and defaults the tail rather than rejecting every save anybody has.

Sparse, and sorted by tile, so a house nobody has painted costs one byte and two identical houses save identically whatever order their tiles were painted in. A tile with no entry draws by the rule it draws by today, which is [OS-yard]: house, yard or street. An older save therefore retains the same default and painted choices. All loaded layouts use the new floor artwork, including historical saves; their covering choices and layout data remain unchanged.

The loader refuses a floor entry off the lot, out of order or repeated, as it refuses a bad wall record: those describe a save that cannot be true. An entry naming a covering the content no longer has is a different thing, a content edit rather than a corrupt save, so that tile loses its covering and the rest of the house loads, exactly as an object whose colourway is gone loads as drawn. Refusing the save instead would make one line removed from `lot.toml` brick every save that used it.

Only a payload that ran out of bytes is padded. Any other decoding failure means the bytes stopped making sense partway, and padding such a payload would rescue a corrupt save rather than an old one: a name whose length byte grew by one eats the floors terminator, and a pad puts one back.

## [FL-draw] Authored materials with stable covering IDs

Boards=1, Tiles=2 and Carpet=3 remain unchanged; Outdoor patio appends ID 4. Zero restores the tile's default. All loaded layouts draw authored material patches with world-aligned phase. Outdoor patio uses rectangular gray paving and does not change a tile's enclosure. Shared world-space diamond corners prevent gaps at fractional pan and zoom. Each tile remains one instance. Unpainted house floors use pale tile, yard uses grass and street uses asphalt. Historical floor sprite data remains unchanged, and the renderer still supports its architecture-disabled compatibility path; the game enables authored floors after Load.

The accepted artwork already contains its starter hue. Runtime content colour tuning is applied relative to that baked baseline, avoiding a second application of the same colour. Finish descriptors separate geometry, pattern and palette; only active alternate patterns consume texture slots. This supports catalogue extension without claiming a new finish library or wall-painting interface.

Outdoor patio uses an append-only descriptor in `assets/models/architecture/outdoor-patio.json`. The offline importer verifies the pinned architecture source and existing material identities before appending it. Accepted export receipts, historical floor geometry, and texture files remain unchanged.

## [FL-tool] The Floors tool

Build offers Floors alongside its other tools, including Land. A click selects and highlights a tile without changing it. Contextual covering buttons apply to that tile; Remove restores its original floor and Clear removes the selection. Number shortcuts apply the corresponding covering only with a selected tile; otherwise they show "Select a tile first." Choosing another tile never paints it automatically. The status line says what the tile is now, or why a change was refused. The tool follows the Walls tool's shape: a controller that previews and stages, a shared contextual surface that writes the buttons, and the simulation owning every decision.

## [FL-area] An area of tiles

Asked for by the owner on 2026-10-19. A second click on another tile, before anything is applied, makes the two clicks the opposite corners of a rectangle and selects every tile in it. Tiles that would take the chosen covering are ringed in the accepted tint and previewed in it; tiles that refuse it are ringed in the refused tint and left out. A covering button, a number shortcut or Remove then stages one `SetFloor` command for every tile in the rectangle that would change and that the simulation accepts, all in one frame. The status line says how many tiles took the covering, and the first refusal's reason when some did not. Once an area is chosen or a change lands, the next click starts a new choice; a second click on the same tile keeps one tile chosen.

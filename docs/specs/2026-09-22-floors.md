# Floors: the player chooses what each tile's floor is

[B-floors] in `FEATURES.md`. Every tile draws the one floor sprite today, recoloured by where it is: the house's own look, the yard's green, the street's grey ([OS-yard], [RC-shift]). The player cannot change any of it. This slice gives them a Floors tool: pick a covering, click a tile, and that tile keeps it.

## [FL-content] A covering is authored content

`content/lot.toml` already carries `yard_look` and `street_look`, each a colour shift of hue, strength and lightness over the one floor sprite. Coverings are a list beside them, each with an id, a plain name for the tool and the same three numbers. The shipped list is short and plain: **Boards**, **Tiles** and **Carpet**, three shifts of the floor art, because there is no floor art beyond that one sprite. The need is logged as [T-floor-art].

A covering's id is its position in that list, so the list grows by appending, and the compiler refuses a list whose names repeat or whose numbers fall outside a colourway's ranges, exactly as it refuses a bad `yard_look`.

## [FL-command] Painting a tile is a command

`SimCommand::SetFloor { x, y, covering }` is appended after the commands that exist, so no earlier wire code moves. `covering` is 0 for "whatever the tile would be without a choice", which is what the Remove button sends, and 1 upward for the coverings in content order. The simulation refuses a tile off the lot and a covering the content does not have.

Like every other lot edit it is applied in stream order, the drain records its result for the tool to read, and it bumps the lot revision so the renderer rebuilds.

## [FL-save] The choices are saved, sparsely, appended last

`SaveSnapshotV3` gains `floors: Vec<(u32, u32, u8)>`, appended last for the reason `sleep_pressure` was: postcard writes a struct's fields back to back, so a payload written before this field existed is a prefix of one written after it, and the loader reads the prefix and defaults the tail rather than rejecting every save anybody has.

Sparse, and sorted by tile, so a house nobody has painted costs one byte and two identical houses save identically whatever order their tiles were painted in. A tile with no entry draws by the rule it draws by today, which is [OS-yard]: house, yard or street. That is how an older save keeps looking exactly as it did.

The loader refuses a floor entry off the lot or naming a covering the content does not have, as it refuses a wall record off the lot.

## [FL-draw] Drawing is one more row in the shift table

`buildStaticInstances` already writes each floor tile's colourway row from a shift table: row 0 the house, row 1 the yard, row 2 the street. The coverings append to that table, so a painted tile writes row 3 upward and everything else is unchanged. No new instance, no new draw, and the sky's shade and the lamp's light are untouched.

## [FL-tool] The Floors tool

Build gains Floors beside Furniture, Walls, Room and Buy. It holds the covering list and a Remove button, and a click paints the tile under the pointer. The status line says what the tile is now, or why a change was refused. The tool follows the Walls tool's shape: a controller that previews and stages, a surface that writes the buttons, and the simulation owning every decision.

## Slices

This slice is the tool, the command, the save and the drawing, with three authored coverings. Painting a whole room in one gesture, a floor that changes what happens on it, and real floor art are each their own later thing; none of them is started here.

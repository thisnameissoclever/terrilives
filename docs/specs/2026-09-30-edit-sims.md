# Edit Sims: change the person without restarting their life

Status: proposed implementation contract for [B-edit-sims], the owner's next
selected feature. Reviewed against main `41341281` on 2026-09-30. No editor is
implemented by this document. The removed-trait policy in [ES-traits] awaits
the owner's answer; its alternatives must not be mistaken for approved behavior.

## [ES-form] Edit the selected living person

An Edit button beside the selected person's identity opens the existing
two-page character dialog in edit mode. Page one contains the current name and
personality. Page two contains the current traits and one relationship selector
for each other living household member. Confirm changes submits one edit;
Cancel and Escape discard it. Back preserves the draft. Opening and closing
the dialog uses the existing pause and focus restoration behavior.

Editing works in a full household. It does not run arrival checks, spawn a
replacement, charge funds, advance time, or issue a new SimId. Needs, position,
career, hobbies, satisfaction, affinity, self-preservation instinct and mortality
records retain their existing values. Creation's Random instinct control is not
shown in edit mode; changing instinct is outside this slice.

Names in the roster, selected-person panel and relationship rows refresh after
acceptance. Confirmation waits for the result of this edit. A refusal leaves
the draft open with a plain explanation. Loading another world closes the draft
and clears pending UI state, so a result from the old world cannot complete it.

## [ES-personality] Preserve unknown personalities

The current runtime and save record hold personality effects, not the authored
archetype identity. Fourteen need multipliers alone cannot identify a personality:
object dispositions and chronotype also matter. The editor must never preselect
personality zero just because the identity is missing.

Proposed representation: add optional authored personality identity beside the
existing effects. New people receive the selected identity. Legacy people are
matched only when their complete saved effects exactly match one current
archetype. An ambiguous or unmatched record uses a literal "Keep current
personality" choice. A name-only edit preserves those effects exactly; the
player can explicitly replace them with one of the current archetypes.

An explicit change replaces all effects of the personality, including the
chronotype offset. Inspect the current constructor and save restoration paths:
`Personality::with_dispositions` initializes the offset to zero. Do not claim
an exact match or reconstruct a changed personality while dropping that field.
The proposed shared initializer gives newly created people the authored offset
as well. Previously saved people keep their historical zero until the player
explicitly replaces their personality. Test creation and editing through that
same initializer, with a nonzero authored offset in both cases.

Runtime-editable personality must join the deterministic world hash. Include
every behavior-bearing field in canonical order and test each independently.
Names remain presentation-only. Optional identity also needs deterministic
save serialization. Saved effects remain authoritative when content tuning
changes: if the current archetype no longer matches them, present "Keep current
personality" and retain the saved effects. Do not reject a previously valid save
because an archetype was rebalanced. Selecting that archetype explicitly adopts
its current values.

## [ES-traits] Retained progress and the open removal rule

Traits retained at confirmation keep their exact current state. A capability's
state is its learned level; a condition's state is its current severity. A trait
unchecked and rechecked within the same unsubmitted draft was never removed.
A genuinely new trait starts at its authored level or severity, or zero for a
stateless disposition. The form never submits arbitrary state values.

Two policies are available for removal committed in an earlier edit:

1. **Recommended: remember progress.** Store removed states in a separate inactive
   ledger. Re-adding a trait restores that state. Inactive entries neither change
   nor contribute effects. This prevents losing learned capability progress or
   resetting a condition through repeated editing. It requires saved, validated,
   deterministically hashed history, bounded by the content trait count.
2. **Alternative: reset on re-add.** Remove the state entirely. Re-adding starts
   from the content default. This uses less state but discards progress and lets
   editing reset condition severity. The UI must describe this consequence.

The owner was asked to choose between these policies on 2026-09-30. No answer
has been recorded. Implement neither as a silent default. If history is chosen,
never leave removed entries in the active `Traits` component: existing effect
consumers treat every entry there as an active trait.

For an action already in progress, preserve its duration, reservation, outcome
roll and any existing fumble. Subsequent calculations use the edited traits.
At completion, only active matching traits receive progress; removing a trait
does not allow that action to recreate it implicitly. Verify chain resumption
and capability-gated actions before finalizing this behavior.

## [ES-atomic] One validated command

Append an edit command without reordering existing wire discriminants. Identify
the target and living relatives by permanent SimId, resolving the current entity
at the exclusive command drain. Reject missing or retired identities rather than
letting an entity slot reused by a newcomer receive the edit.

The payload contains the trimmed name, an explicit keep-or-replace personality
choice, the selected trait IDs, and explicit relationship assignments for the
living household members shown in the editor. It does not contain needs, trait
progress, funds, or a replacement identity. Bounds apply before queueing and
again before mutation. An invalid field rejects the whole command before any
write or random draw.

Reuse the creation rules for name and content bounds, not its room-for-one and
arrival requirements. Validate unique traits, the tuned maximum, live relatives,
unique relative assignments, supported relationship codes and no self-ties.
Do not silently truncate invalid input. Use a handled-count result separate from
move-ins, correlated with the submitted edit and reset on world replacement.

Relationship assignments replace only the pairs explicitly submitted. Store
each pair once using the existing canonical SimId ordering and inverse relation
rules. Other living pairs and ties to deceased or absent people survive. Do not
copy creation's second-command family submission: a name edit that succeeds
while its family edit fails is not an atomic edit.

## [ES-save] Save the draft command and the accepted person

Current entity records already save names, most personality effects and active
trait states. `SavedPersonality` omits chronotype, and restoration currently
initializes it to zero. Add chronotype storage and optional identity, and inactive
history if selected, through appended save-envelope fields. Historical records
without chronotype retain the existing zero default. Preserve frozen historical
entity and command layouts.
Do not edit V1 records to make the newest editor easier to serialize.

Queued edits must survive saving before the command drain. Save personality and
trait references using authored IDs, not pack positions. Restore invalid or
missing content references so the normal command validator refuses the entire
edit. Include pending edits in the world hash and preserve random-generator state.

Extend canonical decoding and historical-prefix tests for any new V5 tail fields.
Missing whole fields have documented defaults. Truncated records, duplicate
person entries and invalid trait states remain invalid. Treat an unknown or
rebalanced personality archetype as a custom saved personality under
[ES-personality], not a reason to discard the household. Loading must not apply
an edit or advance a tick.

## [ES-evidence] Proof required before delivery

1. Edit a starter and a newcomer, including at full household capacity. Confirm
   the same SimId, location, needs, job, hobbies and relationships survive.
2. Preserve retained trait states bit-for-bit. Exercise removal and re-addition
   across confirmation and save/load according to the chosen policy. Test a
   draft toggle separately from a committed removal.
3. Prefill each current personality correctly. Preserve an unmatched legacy
   personality on a name-only edit. Change its personality explicitly and verify
   actual behavior-bearing fields, including dispositions and nonzero chronotype.
   Round-trip that offset and load a saved archetype after its authored numbers
   change without rewriting the person's effects.
4. Submit mixed valid and invalid edits and prove zero partial mutation. Check
   stale targets, retired IDs, full households, repeated traits and relatives,
   unsupported codes, empty names and length boundaries in release-mode exports.
5. Test every family direction, clearing one pair, retaining unrelated pairs,
   and preserving ties to deceased people.
6. Save before command drain and after acceptance. Load historical fixtures and
   continue the same commands and ticks. Compare the actual edited fields as
   well as deterministic hashes. Delete each load-bearing guard or hash input,
   observe the relevant regression fail, then restore exact source bytes.
7. Exercise active object use, a fumbled action, chain interruption/resumption,
   a conversation and work. Edits must not duplicate payouts, release another
   person's reservation, recreate removed traits or strand a participant.
8. Play the editor in a displayed browser at desktop and narrow phone widths.
   Inspect prefilled identity, both pages, all family rows, disabled/pending
   states, refusal, Cancel, Escape, repeated opening, selection and Load changes.
   Check keyboard focus and touch-sized controls. Record screenshots and
   findings; close task-owned pages and servers in cleanup.

## [ES-code-map] Existing implementation paths

`web/src/ui/housemate-form.ts` owns the two-page form; `web/src/main.ts` owns
its modal lifecycle. `crates/terri-sim/src/household.rs` owns creation validation
and spawning. `crates/terri-sim/src/family.rs` validates family assignments.
`crates/terri-core/src/components.rs` defines runtime traits and personality.
The simulation's `save.rs` and `lib.rs` hold snapshot conversion and hashing;
`crates/terri-wasm/src/lib.rs` holds boundary validation and V5 decoding.
`web/src/bridge.ts` carries projections and commands to the form.

# Build mode: a wall tool

Status: slice [WT-slice-walls-and-doorways] is built, tested and played locally
in PR 95. The played check is [A-wall-tool] in `docs/alpha-feel-notes.md`.

This is the second item of [S-build] in `docs/GAME-SYSTEMS.md` and the "rooms,
walls and doors" part of [B-builder] in `docs/FEATURES.md`. Build mode can move
and turn furniture today (PR 85). It cannot change the house.

## What the player gets

In Build mode the player switches from Furniture to Walls. They point at the
line between two floor tiles, or move to it with the arrow keys, and choose one
of three things for that line: a wall, a doorway, or nothing. The game refuses
a change that would cut furniture in half, wall somebody in, or cut any part of
the house off from the rest, and says why in plain words. The house they build
is saved, and sims route around it.

A room is whatever the walls enclose. There is no room object to create or
name in this slice.

## What already exists, and is reused

* **Walls live on tile edges.** `WallEdge { axis, x, y, doorway }` in
  `crates/terri-core/src/layout.rs` names the boundary between two tiles. A
  doorway is a recorded segment that sims can cross.
* **The house is already saved.** Save V3 stores `SavedLayout::EdgeWallsV1`, the
  full list of edges. A wall edit changes that list and nothing else, so the
  save record does not change. The command enums do: each gains an appended
  variant, so a save taken with a wall edit still staged needs this build to
  read it, as a staged furniture move already did.
* **Lot edits are already ordered.** `PlaceObject` is applied by itself, in the
  order the player issued it, between the orders around it
  (`systems/lot_edit.rs`). A wall edit joins that layer.
* **One validator serves preview and commit.** `validate_placement` rebuilds the
  fixed architecture from the saved layout, proves the live grid matches it, and
  then proves the candidate leaves every sim's route, every object's approach,
  the front door and the door's landing in one connected region. A wall edit
  needs the same proof about a different candidate.
* **The shell redraws the house after a lot edit.** `main.ts` already rebuilds
  wall geometry and lighting when the lot revision moves.

## Decisions

### [WT-command] One command, three states

`SimCommand::SetWallEdge { axis, x, y, state }` is appended to the wire enum
after `PlaceObject`, so every earlier wire code keeps its meaning. `state` is
`Open`, `Wall` or `Doorway`. `SavedCommand` gains the same variant at its end,
because a command staged just before an autosave is saved with the world.

One command with a state, and not three commands, because the three are one
decision about one line and the validator treats them as one candidate.

### [WT-rules] What is refused, and the order of the checks

The checks reuse `PlacementRefusal`'s stable codes, in this order:

1. `InvalidInput`: an axis or state outside its range, or a coordinate that is
   not a whole number. Checked at the boundary, in release builds.
2. `UnsupportedLayout`: the world's layout is not `EdgeWallsV1`, or the live
   grid does not match the saved layout plus the furniture. A legacy household
   keeps its frozen walls; the tool says so instead of guessing.
3. `OutOfBounds`: the edge is not an interior boundary of the lot. The outside
   wall is not editable here; that belongs with [B-outside].
4. `BlockedLanding`: the state is `Wall` and the line is the front door's one
   step in, between the door tile and its landing. Refused whoever lives in
   the house: the loader only needs that step while someone has a job, and the
   first person to take one would otherwise meet a walled-off door.
5. `WallOverlap`: the state is `Wall` and one piece of furniture covers both
   tiles. A doorway or an open line can never cut furniture, so it is not asked.
6. `SimOverlap`: the state is `Wall` and a sim is standing across the line,
   part way between the two tiles.
7. `InUse`: the state is `Wall` and it would come down between a sim and the
   object it is using or the person it is talking to: the sim's tile on one
   side, its target's on the other. The sim would carry on through the wall.
8. `BlockedRoute`, `InaccessibleInteraction`, `BlockedDoor`, `BlockedLanding`:
   exactly the proofs a furniture move must pass, run against the candidate
   grid. These can only fail for `Wall`.
9. The V3 loader's own grid checks, run against the candidate: a failure of
   the front door's checks reports `BlockedLanding`, and any other reports
   `BlockedRoute`. The first review of this slice found two walls that passed
   the checks then in place and left a save that would not load: one between
   where a sim's walk ends and the object it is walking to, and one between the
   front door and its landing while another way in stayed open (now check 4).
   Asking the loader,
   rather than copying its rules, is what makes that class impossible. A test
   over the shipped household tries every line at two points in its day and
   loads the save each accepted wall would leave.

Opening a line or making it a doorway only removes a barrier, so neither is
held to checks 4 to 9. That is deliberate: it lets a player mend a house that
is already cut in two, and removing a barrier cannot make a save unloadable.

Setting a line to the state it already has is accepted and changes nothing,
including the lot revision.

The shared proofs move out of `validate_placement` into one function that both
validators call, `prove_lot_usable`, and so does the check that the live grid
matches the saved layout plus the furniture, `current_layout`. Two copies would
drift.

### [WT-apply] What a committed edit writes

The saved layout's edge list and the grid's edge barrier, together, inside the
exclusive lot-edit drain. An existing record for the line is updated in place;
a new one is appended; `Open` removes the record. The list is never re-sorted,
so two players who make the same edits in the same order have byte-identical
saves.

The lot revision rises by one, which is what makes the shell rebuild wall
geometry, lighting and keyboard targets.

### [WT-hash] The world hash sees the walls

A house the player can change is simulation state. The world hash gains the
saved edges, sorted by line and with their doorway flag, so two worlds that
differ only in a wall or a doorway hash differently, and the same house built in
a different order hashes the same. It is written for every edge-wall world, an
empty one included, because an edge house with no walls and a legacy house are
different saves. No golden vector moves: the golden worlds use legacy cells.

This exposed something the hash had hidden. A V1 record carries no wall edges,
so loading a current world's V1 record rebuilds a house with no walls. Two save
tests round-tripped the shipped house through V1 and asserted the same world
hash, which only held because the hash could not see walls. One now round-trips
through V3, the format the game writes; the other keeps V1 on purpose and
compares the V1 records instead. [L-a-blind-digest-proves-false-equalities] has
the detail.

### [WT-boundary] What crosses to the shell

* `wall_edit_preview(axis, x, y, state)` returns the refusal code, zero for
  valid. It never writes.
* `set_wall_edge(axis, x, y, state)` stages the command and returns whether it
  was staged.
* `last_wall_edit_result()` returns the line, the state and the refusal code of
  the most recent committed or refused edit, so the shell can report a refusal
  that only the commit could see.
* `wall_edges()` already exists and is what the renderer reads.

The first three take `f64` inputs and validate them in release builds, as the
placement calls do.

### [WT-shell] The Walls tool

Build mode gains a tool switch with two values, Furniture and Walls. The wall
tool is its own controller beside the furniture one, because another open pull
request is changing the furniture controller.

* **Pointer and touch:** a tap on the floor picks the nearest line between two
  tiles; a tap off the lot picks nothing. The lot tiles beside the chosen line
  are ringed, in the valid or the invalid tint the furniture preview already
  uses. The lot's outer lines can be chosen, by pointer or by arrow keys, and
  the status line then says only that the outside wall cannot be changed here.
* **Keyboard:** arrow keys move the chosen line one step; `H` and `V` choose
  between a horizontal and a vertical line; `W`, `D` and `Backspace` ask for a
  wall, a doorway and nothing. `Escape` clears the choice, and a second
  `Escape` leaves Build mode as it does for furniture. Every other key is
  kept from the furniture tool while Walls is showing, so `]` or `Enter`
  cannot move furniture the player cannot see is selected.
* **Blocked:** while another pause holds, such as a Load in progress, nothing
  can be staged, exactly as for furniture. A press of Walls while a furniture
  move is on its way does nothing; the move lands on the next frame and a
  second press switches. Escape while a wall edit is on its way keeps the
  choice, so the edit's result is still reported.
* **Three buttons:** Wall, Doorway and Remove. Each is disabled when the line
  already has that state, and when the preview refuses it; the status line
  carries the reason.

An edit applies when its button is pressed. There is no separate Confirm,
because a line has no in-between position to hold the way a dragged sofa does,
and Undo is the opposite button.

Every refusal has one plain sentence, listed in
`docs/player-visible-strings.md`.

### [WT-art] What this does with existing art

Walls and doorways already draw from the edge list with the art the house has
today. The slice adds no art. A hinged interior door with open and close frames,
like the front door's, needs authored art and is logged in `docs/TIM-TODO.md`.

## Slices

* **[WT-slice-walls-and-doorways]** Everything above, in one pull request.
* **[WT-slice-room-rectangle]** Drag out a rectangle and wall its outline in one
  edit, with a doorway where the player asks for one. Needs a multi-edge
  command so the whole outline is one validated transaction.
* **[WT-slice-interior-doors]** Doors as hinged objects on a doorway. Waits on
  art.

## What this does not do

Floors and wall coverings, windows, a larger lot, a second storey, buying and
selling furniture, and the outside wall. Each is its own entry in [S-build].

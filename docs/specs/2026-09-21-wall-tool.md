# Build mode: a wall tool

The Walls tool edits saved edge geometry in the current Build draft. Original and player-built walls have the same rules, including perimeter walls. Physical refusals and access review have separate purposes. See [RD-root] in `2026-09-22-reach-from-the-door.md` for the current access contract.

The original [WT-slice-walls-and-doorways] shipped in PR 95. Its played check is [A-wall-tool] in `docs/alpha-feel-notes.md`. That release introduced wall editing before the later Room, window, floor, land and Build confirmation work.

## What the player gets

Choose Walls in Build mode, select a wall line or a run, and choose Wall, Doorway or Remove beside the selection. Windows opens the model chooser. The game previews physical validity and reports a refusal beside the active work. Confirm at the Build footer reviews and commits the combined draft.

A valid change can disconnect ground, people or an object's approaches. Build highlights the affected ground and asks for acknowledgment before committing. The player can choose Confirm or Return to build mode; Escape returns to the draft. Empty enclosed ground can also require acknowledgment. No original door or landing serves as a protected root.

A room follows enclosed saved geometry. The Room tool and room-identity review have their own contracts; using Walls does not require creating a separate room object first.

## Shared foundations

1. `WallEdge { axis, x, y, doorway }` records a boundary segment. A doorway permits crossing; a solid wall blocks it. Typed windows retain their canonical span and block movement.
2. The saved layout and movement grid must agree with placed furniture. Preview and application use the same native validator. Current public save adoption materializes historical implied geometry before editing.
3. Ordered lot-edit commands update the draft. Each controller retains its own selection and native result. Build preparation owns the final candidate and access acknowledgment.
4. A changed lot revision invalidates geometry, lighting and keyboard-target projections. Presentation follows current saved edges and surfaces.

## Decisions

### [WT-command] Stable commands and states

`SimCommand::SetWallEdge { axis, x, y, state }` and its saved counterpart retain their wire identities. The original states are Open, Wall and Doorway; the later Window state remains supported. Typed FitWindow and RemoveWindow commands own current window model and span changes. New commands and variants append without renumbering released codes.

One edge-state command expresses one line decision. A run stages bounded batches of those decisions, while the Room tool uses its own complete-outline transaction.

### [WT-rules] Current validation and historical guards

The native boundary rejects invalid axes, states and nonintegral coordinates. The validator then requires supported edge geometry and a live grid consistent with the saved layout and furniture. Lines must lie within the physical lot bounds. Current perimeter lines on all four sides may be walls, doors, windows or openings; they do not create ground outside the lot.

For a new solid barrier, validation checks furniture crossing, visible people straddling the line, and physical contact with the object or person currently being used. A hidden worker's retained coordinate does not become a construction body. A live path and malformed occupied state retain the applicable validation. Candidate-load checks prevent an accepted edit from creating structurally invalid saved state.

An original doorway, its landing and an old street exit have no current protection. Current access analysis belongs to Build preparation and its exact candidate acknowledgment. Valid disconnected ground is reviewable; it is not itself a physical refusal. A construction command outside an explicit Build session cannot silently approve a newly inaccessible layout.

Window ownership is atomic. Editing any covered line resolves its whole owner. Remove opens the affected span. A Doorway edit opens the clicked segment and restores the remaining window span to solid wall. The complete resulting layout is validated before publication.

Setting a line to its existing state succeeds without changing the layout or lot revision.

Frozen historical validators retain their original entrance, landing and implicit-shell rules. Stable refusal codes such as BlockedDoor and BlockedLanding remain available to those readers. Their identifiers do not grant current assets special status. The original wall release also exercised the loader against candidate grids to catch invalid interaction endpoints; that compatibility evidence remains specific to its inspected revision.

### [WT-apply] What a committed edit writes

The saved layout's edge list and the grid's edge barrier, together, inside the
exclusive lot-edit drain. An existing record for the line is updated in place;
a new one is appended; `Open` removes the record. The list is never re-sorted,
so two players who make the same edits in the same order have byte-identical
saves.

The lot revision rises by one, which is what makes the shell rebuild wall
geometry, lighting and keyboard targets.

### [WT-hash] The world hash includes saved walls

A world the player can change includes its saved architecture in the simulation hash. Wall edges are projected in sorted line order with their doorway flags, so equivalent geometry hashes alike despite insertion order. Windows and explicit surfaces retain their own current hash contributions.

The original release exposed a false equality in older tests: a V1 record omitted edge walls, so it could not round-trip a later edge-wall world faithfully. Its tests were split between an edge-wall-format roundtrip and an intentionally historical V1 record comparison. [L-a-blind-digest-proves-false-equalities] records that reasoning. Frozen golden inputs remain evidence of their original format.

### [WT-boundary] What crosses to the shell

* `wall_edit_preview(axis, x, y, state)` returns the refusal code, zero for
  valid. It never writes.
* `set_wall_edge(axis, x, y, state)` stages the command and returns whether it
  was staged.
* `last_wall_edit_result()` returns the line, the state and the refusal code of
  the most recent committed or refused edit, so the shell can report a refusal
  that only the commit could see.
* `wall_edges()` already exists and is what the renderer reads.

The first three take `f64` inputs and validate them in release builds, as the
placement calls do.

### [WT-shell] Selection and contextual controls

The Walls controller owns its selected line or run, previews, pending batches and native results. Pointer selection uses the drawn wall or nearest floor edge under [WB-pick] in `2026-09-22-walls-in-build.md`. The selected lines carry the [WB-mark] highlight. Perimeter lines are selectable through pointer or keyboard.

1. **[WT-run] Runs.** A second aligned click selects the lines between the endpoints. When clicks move clearly along one axis, the tool derives the nearest shared row or column. Wall, Doorway and Remove act on applicable changed lines in bounded batches. Contextual feedback reports the actual count and any refusal. Windows are fitted one owner at a time.
2. **Keyboard.** Arrow keys move the selection. H and V select its axis. W requests Wall, D requests Doorway, and Backspace or Delete requests Remove. N enters window selection when that chooser is available. Escape clears a settled selection; later Escape follows Build's exit flow. A pending result retains its owner until the controller observes it.
3. **Availability.** Unchanged states, physical refusals, a pending edit and blocking operations disable the corresponding action. An enabled control must perform its named action. The contextual reason identifies the actual restriction.
4. **Feedback.** Useful outcomes appear beside the active selection or in the main-scene feedback owner. Shortcuts remain in the collapsible reference. Assistive status must describe the current operation without leaving stale loading text.

Each successful wall action changes the Build draft. Footer Confirm performs combined room/access preparation and final commit. Cancel follows the Build transaction's discard behavior. A wall action does not bypass final access review.

Player-visible refusal wording is inventoried in `docs/player-visible-strings.md`. Full technical errors belong in diagnostics; UI text must remain concise and useful.

### [WT-art] Rendering saved walls and doorways

Wall, window and hinged-door rendering follows current saved geometry. Doorways on either axis use the ordinary registered art and crossing state. No original door row suppresses a replacement doorway or confers a travel role. See `2026-09-22-interior-doors.md`, `2026-09-22-walls-in-build.md` and the architecture art contract.

## Scope

Walls changes edge geometry. Floor coverings, typed window selection, room outlines, land expansion and furniture placement retain their specialized controls and validators. This specification does not add wall finishes or another storey.

## Current contextual controls

The [approved build controls revision](2026-10-01-build-context-controls.md) places edit actions beside the active selection and puts bindings in a collapsed Shortcuts reference. Controllers retain commands and validation. Wall rotation changes only the selected orientation. Room Doorway enters outline-edge selection; Corners restarts without building.

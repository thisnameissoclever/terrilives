# Build mode: buying and selling furniture

Status: [BM-slice-buy] is built in PR 96: prices, the catalogue and buying.
[BM-slice-sell] is next. It builds on the wall tool (PR 95), which shares the
furniture validator's layout check and usability proofs.

This is the Buy mode bullet of M1 in `docs/FEATURES.md` ("catalog, placement,
rotation, palette recolors") and item 1 of [S-build] in `docs/GAME-SYSTEMS.md`.
Build mode can move and turn furniture (PR 85) and change walls (PR 95). It
cannot add a piece of furniture or take one away, and nothing in the game has a
price.

## What the player gets

* **A catalogue.** Build mode gains a third tool, Buy. It lists every object
  the game can place, with its price, and greys out what the household cannot
  afford.
* **Buying.** The player picks an item, points at the floor, turns it through
  the directions its art supports, and confirms. The price comes out of Funds.
  The same rules as moving furniture decide where it may go.
* **Selling.** With a placed object selected in the Furniture tool, a Sell
  button removes it and pays back part of its price. An object in use cannot be
  sold.

Recolours are the last slice, [BM-slice-recolour]; which palettes to offer
needs the owner.

## What already exists, and is reused

* **Saves are entity lists.** A bought object is saved like any other: by its
  id, position and facing. The loader already restores entity lists with holes
  in their numbering. No save record changes.
* **Placement rules.** `validate_placement` proves a candidate rectangle fits,
  keeps every approach and route, and leaves the door clear, against the
  shared `current_layout` and `prove_lot_usable` (PR 95). A purchase is a
  placement with no existing object to move, so the two share one function,
  `plan_rectangle`, which takes the object being moved or none. Like a wall
  edit, it also runs the V3 loader's own grid checks on the candidate
  ([L-an-edit-must-pass-the-loader]). For what a furniture edit adds, those
  checks are implied today by the move's proofs; they are kept so a rule the
  loader gains later applies here without a second edit. They also refuse any
  edit in a world that already fails the loader, which the proofs alone would
  accept: `a_lot_edit_is_held_only_to_the_grid_checks_its_own_loader_runs`
  fails if the call is deleted. What proves the property is a test that buys a chair on every tile the
  shipped household accepts, at two ticks, and loads each resulting save. The
  checks run under the loader's own conditions: the edge-wall checks only for
  an edge-wall house, as `finish_restore` runs them, so an older cell-wall
  house is never held to a rule its own Load does not apply.
* **The preview.** The furniture preview already draws a ghost of an object
  at a candidate position in the valid or invalid tint.
* **Funds** is simulation state, saved and hashed.

## Decisions

### [BM-price] A price is content

`price` is an optional field on each object in `content/objects.toml`, a whole
number of Funds, compiled onto `CompiledObject` at its end. An object without
a price is not in the catalogue. Prices are not in the save compatibility
digest: a save stores Funds, never prices, so repricing changes nothing an old
save means.

The resale fraction, what selling pays back, is a tunable in
`content/tuning.toml`.

### [BM-buy] Buying is a lot edit

`SimCommand::BuyObject { definition, x, y, facing }` names a pack object index
and is appended after `SetWallEdge`; its wire bytes are pinned by the golden
vector in `crates/terri-core/src/command.rs`. The field is `definition` rather
than `object` because `object` names a placed entity everywhere else on the
wire. It drains as a lot edit, in stream order. It is refused, with the
placement refusal codes plus one new code, when:

1. the index names no priced object (`UnknownObject`);
2. the facing has no art (`UnsupportedFacing`);
3. the household cannot afford it (`CannotAfford`, appended as code 14);
4. any placement rule fails for the candidate rectangle, exactly as for a move.

On success it spawns the object, blocks its tiles, and takes the price from
Funds, in one drain. Exactly the price is enough. The drain records what it
did in `LotEditState::last_purchase_result`, with the new object's entity
index, which the shell reads the way the Walls tool reads its result.

**A purchase staged at save time is saved by object id.** The save
compatibility digest covers the set of object ids but not their order, so a
pack index saved today could name a different object after `objects.toml` is
reordered. `SavedCommand::BuyObject` therefore carries `definition:
Option<String>`. An index that named no object at all saves as `None`, and an
id the pack no longer has (possible only through a reviewed content bridge)
restores as an index past every object; both drain as `UnknownObject`, as the
original command would have. The world hash reads a staged purchase by the
same id, so a save and load never moves the digest.

### [BM-hash] The world hash sees which object each placed entity is

Before buying, the lot content fixed each object's kind, and the world hash
never read it. A radio and a desk chair bought for the same tile at the same
price left equal hashes and different saves. The hash now writes an
object-kinds section: every `SmartObject` entity's index and a digest of its
object id, sorted by index. By id rather than pack index, as a staged purchase
is. It moved the golden world hash, native and wasm alike, from
0xC7BB_234C_419A_654C to 0xA592_DBD9_C174_B14A.

### [BM-sell] Selling is a lot edit, and the first thing that despawns

`SimCommand::SellObject { object }` is appended after `BuyObject`. It is
refused when the object is reserved, targeted, or named by any queued order;
otherwise it despawns the object, opens its tiles, and adds the resale value
to Funds.

This is the first despawn in the game. The render buffer's comment on entity
reuse names the hazard: a later spawn can take the sold object's index, keep
its slot, and be drawn gliding from the old object's position. The fix it asks
for, keeping the previous frame's sorted index list and reseeding on any
difference, ships in this slice with a test.

**A second hazard, found in review of [BM-slice-buy]: entity indices after a
Load.** The loader spawns a placeholder for every gap in the saved entity
numbering and then despawns them in ascending order, and the ECS reuses the
most recently freed index first. Continuous play frees them in the order
things were sold, so the two can hand the next spawn different indices: the
review despawned 38 and then 37, and the next spawn took 37 in continuous play
and 38 after a Load. So after two sales, a save and a Load, the next purchase can
take a different index than it would have without the Load, and the world hash
diverges from continuous play. Nothing despawns before this slice, so buying
alone cannot reach it. This slice must decide it before it ships; one option is
an appended save field listing freed indices in the order they were freed,
which the loader follows when it despawns placeholders.

### [BM-shell] The Buy tool

A third tool button, Buy, beside Furniture and Walls. A list of priced objects
by name, each with its price in brackets; items the household cannot afford
are disabled. Choosing one draws its ghost mid-lot, or where the last ghost
stood; a click or tap moves the ghost; the arrow keys move it; R turns it;
Buy buys; Cancel drops it. After a purchase the choice stays, so a second
chair is one click and one press away. `[` and `]` step through what the
household can afford, skipping what the list greys out. Setting the list back
to its placeholder drops the choice. Pressing any of the three tool buttons
gives the game view keyboard focus, as entering Build mode does.
The Furniture tool gains Sell in [BM-slice-sell].

The switch between the three tools is its own small class in
`web/src/ui/build-tools.ts`, with the key router every Build mode key goes
through; the Walls tool's controls keep only the wall buttons. Leaving a tool
with a purchase on its way keeps it until the drain reports it, as the Walls
tool does.

## Slices

* **[BM-slice-buy]** Prices, the catalogue and buying. Built in PR 96.
* **[BM-slice-sell]** Selling, with the despawn and render reuse fix. Built
  on branch `twcl/sell-furniture`; its design is
  `docs/specs/2026-09-22-selling-furniture.md`.
* **[BM-slice-recolour]** Palette recolours, the last part of the Buy mode
  bullet. The code-owned part is a colourway per placed object, saved and
  hashed, which the renderer applies to the object's existing art through a
  palette map, and a choice of colourway in the Buy tool. Which palettes to
  offer is the owner's taste and is logged as [T-recolour-palettes] in
  `docs/TIM-TODO.md`; the mechanism ships with plain placeholder palettes
  drawn from the approved one.

## What this does not do

A larger catalogue than the objects the game already has art for, starting
money, and any change to what jobs pay. Recolours are a later slice of this
design, not part of the first two.
